# SMV/I263 VLC Reverse-Engineering — Research Log

Goal: build a clean-room, open-sourceable decoder for the proprietary
macroblock/coefficient entropy coding used by the SmithMicro-customised Intel
I263 encoder, so `Nana playing conputer.smv` (and similar VideoLink Mail
files) can be converted to MP4 without depending on the original proprietary
codec. See `CLAUDE.md` for how we got here — this file is where the actual
reverse-engineering work is tracked, session to session.

**Read this whole file before starting work.** Then jump to "Current State &
Next Action" at the bottom — that's the only section you strictly need to act
on; everything above it is reference/justification for why we're doing what
we're doing.

---

## 1. What's already proven (do not re-derive these)

- The file is H.263-family video: PSC `0000000000000000100000`, byte-aligned,
  9,367 frames, ~6,300 bytes/frame, QCIF 176×144, ~10fps, ~16 minutes.
- **The picture header is 100% standard H.263 and parses correctly** —
  confirmed independently by FFmpeg (`h263` decoder reports `176x144` from the
  *unmodified* bytes) and by `bitreader.decode_picture_header()` (which
  mirrors FFmpeg's field layout and is unit-tested against frame 0's known
  values — see "header-is-standard" ledger entry below). **Do not waste a
  session re-litigating the header.** The header for every sample frame ends
  exactly **50 bits into the frame** (see `samples/manifest.json`'s
  `mb_data_bit_offset_within_frame`), i.e. macroblock/GOB data starts at
  absolute bit `frame_byte_offset*8 + 50`.
- The failure is in the **macroblock entropy layer**: FFmpeg's `h263` decoder
  starts decoding macroblocks and throws VLC-table errors within the first
  ~10 MBs of every frame (`illegal ac vlc code`, `run overflow`, `illegal dc`,
  `cbpy damaged` — different error each frame, which itself is informative,
  see open questions). FFmpeg's dedicated `h263i` ("Intel H.263") decoder
  *also* produces 100% blank output, so this isn't merely "use the Intel
  variant" — the deviation is deeper/different than what `h263i` expects too.
- Both `h263` and `h263i` decoders are confirmed available via PyAV
  (`av.codec.Codec(name, 'r')`).

## 2. Tools & shared code (use these, don't reinvent)

- **`bitreader.py`** — the canonical MSB-first bit reader. `BitReader` for
  sequential parsing, `read_bits()` for one-off probes, `find_psc_offsets()`
  for frame boundary detection, `decode_picture_header()` for the
  known-correct header parse. **All new scripts should import from this
  module** rather than redefining `get_bits`. (The original PTYPE miscount
  happened because every script had its own slightly-different bit reader.)
- **`samples/`** — 15 frozen representative frames (raw bytes, PSC-to-PSC) +
  `manifest.json` with offsets/TR/header-end-bit for each. Generated by
  `extract_samples.py`. Use these instead of re-scanning the 62MB source —
  they're small, version-controllable, and consistent across sessions.
  Indices 0-4 are the first 5 frames (where FFmpeg's specific VLC errors were
  already characterized — frame 0 fails at MB 2 with "illegal ac vlc code",
  frame 1 at MB 8 with "run overflow", etc — useful ground truth for "did my
  candidate table at least get further than FFmpeg's stock one"). The rest
  are evenly spread through the file for variety (different TR/motion/scene
  content).
- **`raw_h263.bin`** — full 62MB raw stream from offset 454 (still present;
  fine to use for full-file experiments, but prefer `samples/` for iteration).
- **`tcoef_tables.py`** — TABLE 13/H.263 (TCOEF VLC, 102 entries + ESCAPE) and
  TABLE 14/H.263 (RUN/LEVEL FLC after escape), sourced verbatim from the spec
  and validated (102 entries, genuine prefix-free code, Kraft sum ≈ 0.998,
  `decode_level_flc` matches every worked example in the spec text). Needed
  for M3 / extending the chain walker past TCOEFF blocks.

### Current blocker (historical — resolved in session 4: H2 confirmed, then superseded by the table-completion approach)

The assumption that "INTRADC is safe even in drift-affected MBs because it is read
before any TCOEF VLC scan" turns out to be false in practice. INTRADC is only
safe if **MCBPC and CBPY were also decoded correctly**. If CBPY is wrong (wrong
coded-block flags), INTRADC for later blocks in the MB is read from inside the
TCOEF bitstream of earlier blocks — which passes the forbidden-byte check ~95% of
the time and gives garbage values.

Two hypotheses, not yet discriminated:

**H1 — CBPY inversion missing.** H.263 spec (Table 10 note) and FFmpeg
(`cbpy ^= 0xf` in `ff_h263_decode_mb`) both state that CBPY bits are inverted
for INTRA MBs. Our decoder does NOT invert. If the encoder followed the spec, our
coded-block flags are all backwards, and INTRADC for blocks 2–6 is read from
inside the previous block's TCOEF data.

**H2 — Self-sync false positives in drift correction.** The `score_start` function
accepts any position where 6 consecutive MBs parse structurally. The INTRADC
validity check (byte != 0x00, != 0x80) passes ~95% of the time for random bytes,
so many wrong positions score 6/6. The true MB start might score the same as a
false positive 48 bits earlier.

The previous session noted that tcoef_stats.py got 5/5 plausibility checks WITHOUT
the CBPY inversion. That is evidence AGAINST H1 (either the encoder skips the
inversion, or those early MBs happened to have no coded blocks). H2 is still wide
open.

**Port: `i263_decoder.py`** — faithful Python port of the entropy layer
(parses the C tables directly from `i263_src/` at import; intra pictures;
optional GOB headers; MSB-first bit order verified against `BitStream.cpp`).

**Finding 1 — I263's TCOEF LUT is EXACTLY TABLE 13 (+sign-folding).**
`table_diff.py` compared all 8192 13-bit windows: **8192/8192 agree** on
(length, LAST, RUN, |level|). Sign is folded into the code's last bit /
level-index LSB (lev_tab stores ±value pairs) — total consumption identical
to TABLE-13-code+sign-bit. So our entire TABLE-13-based analysis used the
correct baseline, and "I263" (this build) has standard entropy coding.
The SMV extensions are SmithMicro/VideoLink-specific (or a different Intel
build/draft — MultimediaWiki says I263 follows "early drafts" of H.263).

**Finding 2 — the LUT architecture pins down the extension space.**
`vlc_tab5[show13 >> 5]` handles codes outside `000…`; windows starting `000`
route to `vlc_tab6[show13]` (12/13-bit codes with 8–9 leading zeros live at
indices 16–31); **indices 0–15 (9+ leading zeros) are INVALID** = exactly the
space where SMV's known codes sit (`000000000100` → tab6[8..9],
`000000000101` → tab6[10..11]). Under sign-folding, the SMV extension is at
most **4 code pairs** (tab6[8..9], [10..11], [12..13], [14..15]) with
unknowns (skip∈{12,13}, LAST, RUN, levidx) per pair — a tiny finite space.
NOTE: the two known codes may be ONE ± pair (`00000000010s`), in which case
prior "LAST=0 vs LAST=1" placeholder assignments (from self-sync-polluted
brute force) should be re-derived, not trusted.

**Finding 3 — run-overflow signature localizes the silent divergences.**
Running the port (= TABLE 13 + proper run-overflow enforcement, like FFmpeg)
on all 15 samples: failures at mean ~2 MBs, several at MB 0, all overflows
with coef_num already 48–63 — i.e., blocks decode far too many events
without LAST because an earlier event in the SAME block was silently
mis-consumed. frame_00000 fails at bit 1593, window `0000000001010` — byte
-for-byte our old failure. Conclusion: besides the 4 deep-zero pairs, some
codes in the **6–8-leading-zero region** (where TABLE 13 has rare long
codes) must differ from TABLE 13 in (run/last/length).

**Other port details that matter for the eventual decoder:**
- INTRADC: 8-bit FLC, 0x00/0x80 forbidden, **0xFF decodes as 0x80** (remap
  our reconstruction didn't know), DC coefficient = value<<3.
- Levels are reconstruction values via `lev_tab[levidx + 32*quant]`
  (quant-scaled odd multiples); ESCAPE levels dequantized inline.
- MCBPC intra LUT = TABLE 4 exactly; CBPY LUT carries intra mapping at
  bits 12–15 (= our table, no inversion) and inter (inverted) at 8–11 —
  fully confirms the H1 rejection.
- DQUANT diffs: `[-1, -2, 1, 2]` (standard).

### Session 9, part 3 — regime-tension test: two-syntax model CONFIRMED; first known-plaintext pairs (ledger #35)

Executed the regime-tension test (`regime_tension.py`, 1,432 clean failing
53–200-bit gaps). Full numbers in ledger #35. The three findings:

1. **"Static ⇒ standard" is real, not selection bias.** No fresh payload
   EVER recurs in the immediately-next frame (0/1,432) — static
   bit-copies of proprietary encodings do not exist. When content holds
   still across adjacent frames, the encoder emits a STANDARD encoding.
2. **The encoder is deterministic per (content, changed?) state.** 4.1% of
   fresh payloads recur bit-identically at NON-adjacent frames (oscillating
   content states re-emit the same proprietary bits); 2.3% also occur in
   earlier frames. So "bit-copy while static" was never the mechanism —
   identical inputs simply produce identical outputs, and the syntax is
   gated by changed-vs-previous-frame.
3. **KNOWN PLAINTEXT EXISTS.** For 4 gaps, the same grid MB's frame-(i+1)
   encoding parses fully standard — the encoder judged the content
   UNCHANGED from frame i, which certifies that the standard decode's
   coefficients are what the frame-i proprietary payload encodes. Aligned
   inspection shows prop/std encodings nearly identical (length diffs
   −7..+3, long shared stretches): the proprietary syntax = standard
   grammar with a few substituted events per MB.

This resolves the #31 open question ("how does one decoder distinguish the
regimes in-stream") in the only way left standing: the two syntaxes are
nearly the same grammar; the deviations are a bounded set of substituted
codes, and the decoder presumably distinguishes them the same way we now
can — via codes living in otherwise-unused or re-mapped positions. The
plaintext-alignment attack can now read those codes off directly.

### Session 11 (2026-08-03) — SOLVED: it was a container, not a codec (ledger #37)

Executed session-11 action #1 (plaintext-alignment mining) — and it cracked
the whole problem in one chain:

1. `pair_mining.py`: all 25 insertion pairs admit the CONSTANT inserted
   value `01010110` (0x56) — but canonical positions sat at arbitrary
   offsets inside grammar events, and pairs with identical DC content put
   the marker in different places. Grammar-independent ⇒ tested stream-
   position alignment: **in all 25/25 pairs the 0x56 hit is byte-aligned.**
2. Marker byte positions all ≡ 4 (mod 5) in `raw_h263.bin` coordinates;
   raw scan showed grid-aligned 0x56 every **65 bytes**, deviations of
   exactly +25k, and **0x41 ('A') at +65 inside every deviant interval**.
3. Model: VLMUX packets — `'V' + 64B video payload`, `'A' + 24B audio
   payload`, first 'V' tag at file offset 453 (the "452-byte header" is
   really 453 bytes; PSC at 454 is the first video payload byte).
   `depacket.py` walked the whole 62MB file deterministically: **zero bad
   tags** (941,059 V / 36,812 A).
4. `video.h263` (concatenated V payloads) is **plain standard H.263**:
   stock FFmpeg decodes **10,208 frames, 0 errors**. All prior "proprietary
   VLC" symptoms were mux tag bytes interrupting the bitstream. The old
   9,367-frame count was PSCs that survived tag-byte splitting.
5. `audio.raw` (concatenated A payloads) is **G.723.1 6.3kbps** (24-byte
   30ms frames): decodes completely, 1104.4s — the file HAS sound.
6. Deliverables: `assemble_mp4.py` (H.264, faithful VFR timing from TR
